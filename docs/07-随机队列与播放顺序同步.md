# 随机播放：播放列表面板 = 实际播放顺序

## 现象

1. **随机模式下，播放列表面板里的顺序和实际播放顺序对不上**：面板显示的是队列原顺序
   （或某一次的随机顺序），真正播的却是另一套顺序 —— 看不到"下一首是谁"；
2. 已经播着歌时换歌单 / 切到随机，**当前这首会被切断**（进度清零、从头开始）；
3. 换歌单后"下一首"会**跳到不相干的歌**（`playIndex` 被归零）。

## 根因（都在播放内核 react-jinke-music-player 里）

| # | 位置 | 原因 |
|---|---|---|
| 1 | `handlePlay` 的 `shufflePlay` | 内核的"随机"不是随机的，而是**一个预先算好的乱序索引表** `shuffledAudioListIndex`。播放按索引表走，面板渲染的却是队列数组本身 → 两者天生不同步 |
| 2 | `UNSAFE_componentWillReceiveProps` | 列表被整体替换时无条件 `updatePlayIndex(DEFAULT_PLAY_INDEX=0)`，和 `loadNewAudioLists(newAudioListPlayIndex)` 抢跑，把 `playIndex` 拍回 0 |
| 3 | `changeAudioLists` / `loadNewAudioLists` | 换列表时先 `resetAudioStatus()` + `resetPlayId()`：即使只是"重排一下队列"，也会暂停、清空并重新解析 `musicSrc`（进度清零） |
| 4 | `getPlayInfoOfNewList` | 认领旧播放项 key 时只比 `musicSrc`；本项目的歌单项没有 `musicSrc`（由 `musicSrcParser` 现解析）→ 所有项都匹配到同一个旧项，key 会重复/每次重排都变 |

另外，上一版的"预排队列"只在**点歌 / 播歌单**两条路径上生效，**启动**（`initPlayer`）和
**全歌单播放**（`ShuffleAllButton` 走的是 `playMode` 兜底）没走同一条路，所以那里依旧是内核实时随机。

## 方案

**队列是唯一事实来源**：开播前就把顺序定下来，之后播放严格按队列顺序走。

1. `src/utils/PlayQueue.ts`（新增）
   - `queueForPlaylist()`：随机模式下用播放器自带的 **smart shuffle**（`shuffleObjectsNoAdjacentDuplicates`）
     排一次队列；非随机就用歌单原顺序 —— 两条路径都经过它；
   - `withPlayerKeys()`：给队列每一项挂一个**稳定 key**（`bvid-id`），内核重排后依然能认出"还是这首"；
   - `usesPredictableShuffle()` / `rjkmPlayModeFor()`：判断"现在是不是随机"，与内核的 `playMode` 取值对齐；
   - `resyncQueueOrder(playlist)`：切随机 / 切回顺序时**只重排序**（`keepCurrentAudioInList`），
     并校验"这条队列确实属于这张歌单"才动手。
2. `src/hooks/usePlayback.ts`
   - `initPlayer` / `onPlayOneFromFav` / `onPlayAllFromFav` 三条装载路径全部 `queueForPlaylist()`；
   - `updateCurrentAudioList()` 带上 `shuffleAlongAudioLists` 与 `keepCurrentAudioInList`；
   - `onPlayModeChange()`（播放器里的模式按钮）在随机状态变化时调用 `resyncQueueOrder()`。
3. `src/components/Playlist/PlaylistSetting/usePlaylistSetting.ts`
   - 歌单设置里改播放模式 → 保存后同样 `resyncQueueOrder()`。
4. **播放内核配套补丁**：`patch/rjkm-fork-queue-sync.patch`（4 处，都与宿主显式传的开关绑定，
   其他调用方行为不变）

| 补丁 | 作用 |
|---|---|
| `shuffleIndices(length, shuffleAlongAudioLists)` | `shuffleAlongAudioLists=true` 时随机索引表 = 队列原顺序 → **播放顺序 = 面板顺序**，图标仍然是"随机" |
| 稳定 key 优先沿用 | 宿主自带 key 时不再按 `musicSrc` 认领 → key 不再碰撞 |
| `keepCurrentAudioInList` | 只重排时不 `resetAudioStatus` / 不 `resetPlayId`、不重新解析 `musicSrc` → **当前这首继续播** |
| 列表被替换时不调 `updatePlayIndex(0)` | 播哪首交给 `newAudioListPlayIndex`，`playIndex` 不再被归零 |

## 怎么测

### A. 自动化（无头 Edge + 真播放内核）

```bash
node tools/queue-harness/drive.mjs <打了补丁的 NoxPlayer 目录>
```

它会把真内核（`react-jinke-music-player`）挂到无头 Edge 里，模拟宿主改 `audioLists`
并断言 16 条（面板顺序、当前歌不被切断、进度不清零、不重新加载音频、`playIndex` 跟随、
换歌单仍然正常换歌、默认实时随机行为没被破坏）。

### B. 手动验收（3 分钟）

1. 打开播放器，把某张歌单的播放模式切成**随机**（歌单设置里的循环按钮）→ 播放；
2. **点开右下角播放列表面板**：面板里的顺序应与实际播放顺序一致，点"下一首"精确走到面板里
   紧跟其后的那一首（面板里 `▶` 标记的那首就是当前播的）；
3. **在播着歌的时候**切随机 / 切回顺序：正在播的那首**不能中断**，进度条不能回到 0；
4. 换一张歌单播放：应当从那张歌单（随机模式下=随机顺序的第一首）开始，不再出现
   "先闪一下别的歌再切过来"；
5. 连播两首响度差很大的视频，切换瞬间不应有明显音量跳变 —— 单曲内部的动态依旧保留
   （整首只有一个固定增益）。

## 已知限制

- 把设置里的 **`smartShuffle`（智能随机）关掉**时，会退回内核的实时随机 —— 那种情况"下一首"
  确实无法预知，面板顺序也不再等于播放顺序（这是刻意的逃生门）；
- 播放列表面板里**手动拖动排序**只改内核内部顺序，宿主队列与歌单都不动；下一次装载队列
  （切歌单 / 切随机）会按队列顺序重排回来；
- 队列项是**带 key 的副本**（`{...song, __PLAYER_KEY__}`）：只影响播放队列，**不会写回歌单**，
  也不落盘；
- 只有当"正在播的队列的歌与当前歌单的歌完全一致"时才重排，其它情况下只切播放模式；
- 直播源（`biliLive`）不参与，逻辑与响度归一一致。
