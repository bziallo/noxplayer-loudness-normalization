## 1. 一比一对应你的验收标准

| 你的要求 | 实现里靠什么保证 |
|---|---|
| **连续播放两个音量差很大的视频，切换瞬间不应有明显音量跳变** | ① 切歌时增益在 **src 赋值之前**就同步写好（`resolveForPlayback` 跑在 `musicSrcParser` 里），命中缓存的曲目**从第一个采样就是正确音量**；② 未命中时先回 0 dB（原声）→ 测完用 **120 ms `setTargetAtTime` 斜坡**落位，是渐变不是跳变；③ 播放中会**预取下一首**（`prefetchNextLoudness`，列表顺序播放时启动，5 s 后触发），所以常见情况下第二首也是「第一个采样就正确」；④ 预取会写同一份缓存，切过去直接命中 |
| **单个视频内部的爆炸声、音乐起伏应保留，不能被压平** | 全程**只有一个常数增益**：`GainNode.gain` 每首歌只设一次（外加切换时的斜坡），没有 compressor、没有 limiter、没有逐帧 AGC。实测口径：`gainDb` 在整首播放期间是常数（`probe/loudness/check.mjs` 与 §4 的手动步骤都在查这一点）。增益预算只做一件事——**限制提升**（真峰值 ≤ −1 dBTP），衰减永远放行，所以它不可能改变素材动态 |
| 整段测量后固定增益，不要实时动态压缩 | 抽样覆盖 0%–100% 时间轴（12 段均匀分布），算**集成响度**（BS.1770 门限），不是滑动窗口 |
| 复用原脚本算法 | `sidx.js` / `loudness.js` / `gain-planner.js` / `sampler.js` / `audio-engine.js` 逐模块移植成 TypeScript，K 加权系数与 ITU-R BS.1770-4 官方 48 kHz 系数**逐点 0.0000 dB 偏差** |
| 性能要好，不能明显增加卡顿 | 单曲抽样 ≈ **0.5 MB / 60 秒音频**（110 分钟视频实测 0.91%），旧 ffmpeg 路径要下整条音频（那个视频是 54 MB）；响度计算分块让出主线程 |
| 多个响度档案 / 滑条 | 6 档档案（标准 −14 / 高动态 −24 / 耳机 −16 / 外放 −11 / 深夜 −20 / 自定义）+ 目标响度、最大提升、最大衰减三个滑条 |
| 开源协议兼容 | 见 §5 |

## 3. 关键设计

### 3.1 链路

```
musicSrcParser(song)                        ← 播放器换 src 之前
  ├─ 命中内存缓存 → 立刻写 GainNode（immediate），曲目从第 0 个采样就是正确音量
  ├─ 未命中       → 先 0 dB（原声），并异步测量
  └─ B站 CDN 源   → 顺手把 <audio> 设成 crossOrigin='anonymous'

测量（不阻塞播放）
  ① Range 取前 32KiB → 找 sidx（超大索引再补一次 Range，实测 110 分钟视频索引 15.9KB）
  ② 均匀抽 12 段（首段必取），限速并发 6，段超时 5s 重试 1 次
  ③ 每段拼 init+单段 → decodeAudioData（离线上下文，不碰输出）
  ④ 拼 PCM → K 加权 → 400ms/100ms 分块 → 绝对门限 → 相对门限 → 集成 LUFS + 真峰值
  ⑤ 首批满 4 段就先落一次初值（≈19 秒音频、覆盖全片），剩余段补齐后再精修（差 <0.5 dB 不重落）

落位
  <audio> ─► MediaElementAudioSourceNode ─► GainNode(10^(dB/20)) ─► destination
                                              ▲ setTargetAtTime，τ=40ms
  元素自身 volume（播放器滑块）按规范仍然生效，两者相乘
```

### 3.2 几个刻意的选择

- **只对 B站 CDN 源接管**（`bilivideo.com/.cn`、`hdslb.com`、`cgvideo.com`、`acgvideo.com`）。
  YouTube / 本地文件 / alist 一律不接管、不改 `crossOrigin`，零副作用。
  （实测这几个 host 对带 `Origin: chrome-extension://…`、带 Range、**不带 Referer** 的请求都回 `206 + Access-Control-Allow-Origin: *`。）
- **AudioContext 不 running 就绝不接管**（原脚本踩过「永久静音」的坑）→ 先 `resume()`，仍不行就降级。
- **降级链**：GainNode → `element.volume`（只能衰减，且这时会拦住播放器把归一音量存成「用户默认音量」）→ 原声。
- **缓存存的是「这首歌多响」（measuredLufs + truePeakDb），不是「增益」**：所以改目标响度、换档案都不用重测。
  与旧的 `r128gain-table` **分表**：那是 ffmpeg ReplayGain（−18 LUFS 参考系、与手机端同步），混用会互相污染。
- **直播不处理**（无固定时长、无 DASH 索引），沿用旧的 `SkipR128Source` 判断。

### 3.3 你上次定的三件事，具体落成什么样

1. **「可以设多个响度表，类似滑条」**
   `config.ts` 里一张 `DEFAULT_PROFILES` 表（标准/高动态/耳机/外放/深夜/自定义），
   设置面板给三个滑条（目标响度 −28…−8 LUFS、最大提升 0…18 dB、最大衰减 −60…0 dB），
   拖滑条会自动切到「自定义」档——和原脚本面板的行为一致。

2. **「用 ffmpeg 路径」**
   我把 ffmpeg 从「唯一测量方式」改成**可选引擎 + 兜底**，没有删掉任何东西：
   - 设置里可选 `自动（B站抽样 / 其它 ffmpeg）` / `抽样测量（快，约 0.5MB）` / `ffmpeg 全片（慢，最准）`；
   - `自动` 时：B站源走抽样，抽样失败自动回落 ffmpeg；
   - ffmpeg 全片测量照旧是「整段测量后固定增益」，只是会下载并解码完整音频（110 分钟的视频音频 54 MB、几十秒），
     所以默认不当主路径。
   > 如果你的意思是「测量一律走 ffmpeg 全片」，改一个默认值即可：`resolveLoudnessSetting` 里
   > `engine: playerSetting?.loudnessEngine ?? 'ffmpeg'`；或者在设置面板里直接选「ffmpeg 全片」。
   > 需要我直接改成默认 ffmpeg 的话说一声，一分钟的事。

3. **「如果对最终结果无影响可以修」**
   `r128util.ts` 里 B站元数据的符号修了：`loudness = target_i − measured_i`（正值=需要提升）本来被写成 `-source.loudness`，
   导致「越轻的视频调得越小声」。**对最终结果无影响**的依据：扩展侧 `x/player/playurl` 的 `data.volume` 实测恒为 `null`
   （官方实测，见调研文档 §3-E1），所以这条分支在扩展里根本不会触发；新功能也不依赖它（一律本地测量）。
   移动端 `SongOperations.ts:102` 有同样的问题，但那是另一个仓库，我没动。

### 4.1 自动化（不需要 B站 账号、不联网）

```bash
yarn                                  # 首次需要装依赖
node probe/loudness/check.mjs         # 期望：32 passed, 0 failed
yarn compile                          # tsc，无新增错误

```

`check.mjs` 覆盖：sidx 解析（含 `first_offset` 基准点）、K 加权与官方系数比对、多声道求和、门限、
真峰值、增益规划（含「素材已过峰不倒扣音量」这条实测反例）、采样器端到端
（本地 Range 服务器 + 桩解码器：**校验每个请求到的字节偏移真的是 `moof` 盒**、索引超过头部窗口时补第二次 Range、
可用段数不足 3 段时拒绝给结果）。

我这边另外跑过一套更强的验证（不在 patch 里，因为要下载真实音频当样本）：
用两条真实 B 站视频的音频字节 + Python 独立实现的 sidx 解析器当 oracle，**70 条断言全过**：

| 视频 | 时长 | 索引 | 校验结果 |
|---|---|---|---|
| `BV1GJ411x7h7` | 3.5 min | 43 段 × 5.0s，sidx 548 B | 段偏移全落在 `moof` 上；`Σsize+anchor == Content-Length`；抽 12 段 = 311 KiB |
| `BV1muab6rEbA` | 110 min | 1323 段 × 5.0s，sidx **15 916 B**（超 4KB，走二次 Range） | 同上；抽 12 段 = 482 KiB（0.91%） |

### 4.2 手动验收（你要的那两条）

1. **选片**：两条响度差 ≥4 LU 的 B 站视频。调研里用过的组合：
   `BV1GJ411x7h7`（官方 `measured_i ≈ −13.5 LUFS`，偏响）与 `BV1muab6rEbA`（≈ `−18.7 LUFS`、真峰值 +0.79 dBTP，偏轻且已过峰）。
2. 打开「设置 → 播放器设置 → 响度归一」，档案选**标准（−14 LUFS）**。
3. **切换测试**：两条连播（循环 3–5 次），切换瞬间不应有明显音量跳变。
   想看得更细：DevTools 里 `subscribeStatus` 的状态行会显示 `命中缓存 / 已施加固定增益 / 实测 LUFS / 目标 / 增益`，
   第二次起应当是「命中缓存」且增益立即到位。
4. **动态未压平测试**（关键，别只看平均音量）：
   - 在**同一首**里挑「安静段 / 高潮段」分别听与测 RMS，归一前后两者差应基本不变（≤0.3 dB）；
   - `Shift+B` 来回旁路做 A/B：应当只有**整体平移**，没有「一响就压下去」的痕迹；
   - 状态行/`console` 里的 `gainDb` 在整首播放期间应是一个常数，不随时间变化。
5. **回归清单**：音量滑块、进度拖动、上/下一首、播放模式、歌词、睡眠定时、
   `memoryEfficiency`（会重载页面）、切换皮肤、下载。
6. **性能**：首播到增益落位应在 1 s 内（缓存命中≈0）；抽样字节数 ≈0.5 MB/首；播放期间无长任务。

   想在控制台直接看数值，归一模块挂了调试句柄（和原脚本的 `__biliLoudness` 一个路子）：

   ```js
   noxLoudness.getLastStatus()        // { stage, measuredLufs, targetLufs, gainDb, mode, … }
   noxLoudness.engine.getGainValue()  // 当前实际线性增益（整首播放期间应基本不变）
   noxLoudness.engine.getMode()       // 'gain-node' | 'volume' | 'off'
   ```

## 5. 开源协议兼容性（你特别提醒的那点）

先说清事实，再说结论：

| 代码 | 协议 | 依据 |
|---|---|---|
| 响度归一原脚本 `ADMA200/Bilibili_LoudNorm` | **MIT** | 仓库 `LICENSE` 与脚本头 `// @license MIT` |
| 电闹播放器 `lovegaoshi/NoxPlayer` | **AGPL-3.0**（`LICENSE` 文件） | 仓库 `LICENSE` 全文是 GNU AGPL v3 |
| 同上，`package.json` 里写的是 | `"license": "MIT"` | 与 `LICENSE` 文件**不一致**，且 README 的 license 徽章指向 `kenmingwang/azusa-player` 的 MIT |
| 上游 `kenmingwang/azusa-player` / 播放内核 fork | MIT | 各自 `LICENSE` |

**结论：可以合，不会引入不兼容代码。**

- MIT 是最宽松的 permissive 协议，它的代码**可以被并入 AGPL-3.0 工程**（AGPL 的 copyleft 覆盖整个衍生作品，
  MIT 只要求保留版权与许可声明）。反过来（把 AGPL 代码塞进 MIT 工程）才有问题，这里不涉及。
- 因此无论上游最终按 AGPL-3.0 还是按 `package.json` 声明的 MIT 分发，本 patch 都兼容。
- 我做的落实动作：**每个移植文件头部都写明出处 + MIT + `(c) 2026 Moxia9527`**；
  README 增加归属段落；除算法思路外没有复制任何第三方源码；没有引入 GPL/专有代码；
  `package.json` 依赖没有新增（抽样用的是浏览器自带的 `decodeAudioData`，ffmpeg 用的是仓库已有的 `@ffmpeg/*`）。
- **刻意没有改 `azusa-player-mobile` 子模块**：一是技术上一手实测证明「只用音频 URL 就能拿到 sidx」，
  不需要它多吐字段；二是避免把改动扩散到另一个仓库、把协议边界搞复杂。设置类型用 `declare global` 合并，同理。
- ⚠️ 需要你/上游确认一件事：仓库 `LICENSE`(AGPL-3.0) 与 `package.json`(MIT) 不一致，这属于既有问题，
  我在 PR 里只做说明、没有擅自改动协议文件。

## 6. 已知限制

- **纯线性增益，没有压缩器/限幅器**：增益只在「真峰值 ≤ −1 dBTP」内提升，越界只衰减不提升 →
  不会改变动态，但**也不会把已经爆音的素材修好**。
- **不支持直播**；拿不到 DASH（只有 `durl`，例如试看片段）时保持原声。
- **首播仍要等几百毫秒**（抽样+解码），期间播原声；看过的视频命中缓存瞬间落位。
- **抽样是统计估计**：极端不均匀的素材（例如只有结尾 5 秒很响）可能偏差 1–2 LU。
- 测量依赖音频 CDN 可达与可解码；若某档音频解码失败（例如 FLAC/Hi-Res），该次归一会被放弃（保持原声）。
- 缓存表是新增的，**老库升级依赖 `migrateSQL()` 在启动时跑迁移**；万一迁移失败，所有缓存读写都吞异常，
  只会退化成「每次都重测」，不会影响播放。

## 7. 我**没能**验证的部分（避免你误判交付强度）
