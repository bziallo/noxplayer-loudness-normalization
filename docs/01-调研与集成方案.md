# 电闹播放器 × B站响度归一 —— 第一阶段调研与集成方案

> 目标：在【电闹播放器】里，对 B 站视频/音频做**整段测量后的固定增益**归一
> （不做实时压缩、保留原始动态）。本文只做调研与方案，代码待确认后实施。
>
> 调研方式：读源码（三个仓库快照）+ 本机一手实测（B 站接口 / 音频 CDN / fMP4 索引 / 规范原文）。

## 2. 音频链路分析

### 2.1 从歌单到扬声器（现状）

```
歌单 Song {bvid, id(=cid), source}
      │
      ▼
usePlayback.musicSrcParser(song)            src/hooks/usePlayback.ts
      │   fetchPlayUrlPromise()             @APM/utils/mediafetch/resolveURL.ts
      │     └─ regexResolveURLs → 兜底 fetchVideoPlayUrlPromise()
      │          └─ GET x/player/wbi/playurl  (wbi 签名, DNR 注入 Referer/Origin/UA)
      │             返回 { url: dash.audio[best].baseUrl, loudness?: target_i - measured_i }
      ▼
ReactJkMusicPlayer 渲染 <audio class="music-player-audio" src={url}>
      │   元素是**单例复用**的（换歌只换 src）
      │   this.audio.load() → 播放器自己维护 volume = (滑块值)²
      ▼
扬声器
```

关键事实（源码级）：

- **元素身份**：`getAudioInstance={setCurrentAudioInst}` → `currentAudioInst` **就是** `<audio>` DOM 元素
  （RJKM 的 `getEnhanceAudio()` 只是在它身上 `defineProperty` 挂了 `playByIndex/playNext/...`）。
  `App.tsx` 里已经在用 `currentAudioInst.currentTime`、`RJKMref.audio.pause()`。
- **音量语义**：RJKM `setAudioVolume(v) { this.audio.volume = v ** 2 }`，每次 `initPlayer` 会
  `setDefaultAudioVolume()` 重置；`volumechange` → `props.onAudioVolumeChange(volume)` →
  nox 把 `sqrt(volume)` 存回 `playerSetting.defaultVolume`。
- **解析时机**：`musicSrcParser(audioLists[playIndex]).then(loadAudio)` —— 这是**扩展最后能插手、
  且早于 src 赋值**的位置，设置 `crossOrigin` 必须在这里或更早。
- **无 MSE / 无 blob**：播放路径就是「CDN 直链 → `<audio>`」，比 B 站网页端简单
  （网页端是 blob+MSE，脚本必须靠 `__playinfo__` 与 `video.volume` 兜底）。

### 2.2 现有的「响度归一」链路（半套）与缺口

```
playerSetting.r128gain（默认 false，SettingTab 有开关）
      │
      ▼  usePlayback.parseR128Gain()      ← 先 currentAudioInst.volume = 1
      ▼  r128util.getOrSetR128Gain()      ← 先查 pglite 缓存 r128gain-table
      │      ├─ 缓存命中 → r128gain2Volume(val)
      │      └─ 未命中 → ffmpeg.wasm: fetchFile(整条音频) → replaygain 滤镜 → 写缓存
      ▼  setTimeout(500ms) → currentAudioInst.volume = 10^(dB/20)
```

缺口/缺陷（都会在推荐方案里被替换掉）：

1. **成本高**：`fetchFile(url)` 把**整条音频**拉进内存再交给 ffmpeg.wasm 全片解码。
   短歌 1–5 MB 尚可，110 分钟的视频音频实测 **54 MB**（见 §3），解码是几十秒级。
2. **只能衰减**：`r128gain2Volume(gain) = gain > 0 ? 1 : 10^(gain/20)`，`audio.volume` 上限 1.0
   → 比目标响度**轻**的素材永远抬不起来，与「切换时整体音量一致」的目标不符。
3. **污染用户音量**：把归一增益写进 `audio.volume` 会触发 `volumechange`，
   nox 的 `onAudioVolumeChange` 会把它当成用户操作存成 `defaultVolume`，滑块与归一互相打架。
4. **`500 ms` 定时器 + 先置 1**：切换歌曲瞬间音量会跳（先 1.0 → 后落位）。
5. **B 站元数据快路径符号反了**（本次一手发现）：
   `loudness = target_i − measured_i`（正值 = 需要提升），但 `r128util` 用的是 `-source.loudness`
   （`SongOperations.ts:102` 移动端同样 `setR128GainSQL(song.id, -url.loudness)`）。
   例：`measured_i=-23.8, target_i=-14` → 本该 +9.8 dB（或按"只能衰减"钳到 0），
   实际被算成 −9.8 dB → **越轻的视频调得越小声**。
   （该路径默认被 `noBiliR128Gain: true` 关掉，所以少有人踩到。）
6. **扩展侧拿不到官方响度元数据**：一手实测 `x/player/playurl` 的 `data.volume` 为 `null`
   （脚本文档亦记录：元数据只在网页 SSR 的 `__playinfo__` 里）
   ⇒ 桌面扩展实际上**必然**走 ffmpeg 全片路径。

### 2.3 脚本要求的能力 vs 播放器具备的能力

| 脚本需要的 | 电闹播放器现状 | 结论 |
|---|---|---|
| 拿到音频 URL | ✅ `musicSrcParser` 已有 | 直接可用 |
| 读分片索引（sidx） | ✅ `host_permissions` 含 `*.bilivideo.com/.cn`、`*.hdslb.com`、`*.cgvideo.com`、`*.acgvideo.com` | 直接可 fetch |
| 跨域读字节 | ✅ 扩展页带 host 权限 → fetch 不受 CORS 限制；且 CDN 实测 `ACAO: *` | 无风险 |
| 解码 AAC fMP4 分片 | ✅ 扩展页 = 同一 Blink 解码器，`decodeAudioData` 可用 | 与脚本同款做法 |

| 缓存测量结果 | ✅ 已有 pglite(IndexedDB) + drizzle + 启动时 `migrateSQL()` | 加表即可 |

## 3. 一手实测证据（本次会话验证）

> 全部用脚本直连 B 站接口 + 音频 CDN 跑出来，非推测。

**E1｜播放链接与元数据**（`BV1GJ411x7h7`，cid 137649199）

- `x/player/playurl?bvid&cid&platform=web&high_quality=1&fnval=4048` → `code: 0`，`dash.audio` 3 条
  （30216/30232/30280），`SegmentBase = {"Initialization":"0-933","indexRange":"934-1481"}`。
- `data.volume = null` → **扩展侧拿不到官方响度元数据**（FastPath 在桌面端不可用）。

**E2｜CORS 与 Range**（关键可行性证据）

| 请求 | 结果 |
|---|---|
| `GET baseUrl` 带 `Range: bytes=0-1023`、**不带 Origin** | `206`，`ACAO: *`，`Accept-Ranges: bytes`，`Content-Range: bytes 0-1023/5408198` |
| 同上，带 `Origin: chrome-extension://…` | `206`，**`ACAO: *`** |
| 同 host，**不带 Referer** | `206`，`ACAO: *` |
| `OPTIONS` 预检 | `404`（媒体元素请求不触发预检；扩展页 fetch 有 host 权限也不需要预检） |

⇒ `crossOrigin="anonymous"` 不会导致静音；音频 CDN 也不校验 Referer。

**E3｜只用音频 URL 就能拿到分片索引**（决定「要不要改子模块」）

只 `Range: bytes=0-4095`（不带 Referer）：

| 视频 | 时长 | sidx 位置/大小 | 索引自校验 Σsize+first_offset+anchor == Content-Length | 抽样 12 段成本 |
|---|---|---|---|---|
| BV1GJ411x7h7 | 3.5 min | 944 / 548 B | ✅ 1 167 163 B | init 1492 B + 12 段 = **311 KiB**（27%） |
| BV1EV411s7vu | 5.2 min | 942 / 788 B | ✅ 2 645 088 B | init 1730 B + 12 段 = **490 KiB**（19%） |
| BV1muab6rEbA | 110 min | 837 / **15 916 B**（超 4 KB，二次 Range 补齐） | ✅ 54 447 341 B | init 16 753 B + 12 段 = **482 KiB（0.91%）** |

抽查第 0/中/末段的绝对偏移，**全部是 `moof` box**（证明 sidx 锚点算对了）。
⇒ 长视频的 sidx 可能 > 4 KB，做法是「先取 32 KB → 读出 sidx box 的声明长度 → 不够再补一次 Range」，
**不需要** `SegmentBase.indexRange`，**不需要改 `azusa-player-mobile` 子模块**。

**E4｜接管音频后音量滑块还灵吗**（W3C Web Audio 规范原文）：

> "The HTMLMediaElement MUST behave in an identical fashion after the MediaElementAudioSourceNode
> has been created … Thus pausing, seeking, **volume**, src attribute changes, and other aspects of
> the HTMLMediaElement MUST behave as they normally would …"

⇒ 增益放 GainNode，RJKM 的滑块（`audio.volume`）照常生效，二者相乘、互不干扰。
这正是修掉 §2.2 缺陷 3/4 的关键。

## 5. 推荐方案（方案 A：抽样测量 + GainNode 固定增益）

### 5.1 目标链路

```
musicSrcParser(song)
   ├─ 1) 解析 URL（沿用现有链路）
   ├─ 2) 若 host ∈ B站CDN白名单 → 给 <audio> 设 crossOrigin='anonymous'
   ├─ 3) 查缓存 loudness-table(cid)  ──命中──► measuredLufs / truePeakDb
   │                                       └─未命中─► 异步测量（不阻塞播放）
   │                                            ① GET bytes=0-32767 → 定位 sidx（不够再补一次）
   │                                            ② 解析 refs → 均匀抽 12 段（首段必取）
   │                                            ③ 并发(6) Range 拉段 + init，逐段 decodeAudioData
   │                                            ④ K加权 + BS.1770 门限 → 集成 LUFS + 真峰值
   │                                            ⑤ 写缓存
   └─ 4) gain-planner: gain = clamp(目标 − 实测, 峰值预算, 档案上下限)

<audio> ──► MediaElementAudioSourceNode ──► GainNode(10^(gain/20)) ──► destination
                                              ▲ setTargetAtTime, τ=40ms（≈120ms 落位，无跳变）
   元素自身 volume 仍由播放器滑块控制（规范保证），二者相乘
```

### 5.2 移植模块（几乎原样，JS → TS）

| 脚本模块 | nox 新模块 | 处理 |
|---|---|---|
| `loudness.js` | `src/utils/audio/loudness/bs1770.ts` | K 加权（系数按采样率现算）+ 400 ms/100 ms 分块 + 绝对/相对门限 + 真峰值；分块让出主线程 |
| `sidx.js` | `src/utils/audio/loudness/sidx.ts` | fMP4 sidx 解析 + `pickEvenly/pickCoarse` + 索引自校验 |
| `sampler.js` | `src/utils/audio/loudness/sampler.ts` | Range 抓取（AbortController 超时 + 重试 + 限速并发池）+ `init‖seg` 拼 Blob → decodeAudioData；**去掉 GM_xmlhttpRequest 分支**，用扩展 fetch |
| `gain-planner.js` | `src/utils/audio/loudness/gainPlanner.ts` | 增益预算（峰值只约束**提升**，衰减永远放行——脚本踩过坑的修正版） |
| `audio-engine.js` | `src/utils/audio/loudnessEngine.ts` | 精简版：单元素、懒建 AudioContext、`createMediaElementSource` 只做一次、`setTargetAtTime` 斜坡、bypass、**永不 disconnect / 永不 pause** |
| `config.js` 的 profiles | `src/utils/audio/loudnessProfiles.ts` | 标准 −14 / 高动态 −24 / 耳机 −16 / 外放 −11 / 深夜 −20 LUFS + 各自增益上下限 |
| — | `src/utils/audio/normalizeClient.ts` | 编排：读缓存 → 测量 → 定额 → 写缓存（替代 `r128util.ts`） |
| — | `src/utils/db/schema/loudnessTable.ts` | 新表 `loudness-table(songcid, measuredLufs, truePeakDb, gainDb, profile, engineVersion, updatedAt)` |

> 与旧 `r128gain-table` **分表**：旧值是 ffmpeg 的 −18 LUFS 参考系，混用会互相污染；
> 新表还存 `measuredLufs`，**换预设档不必重测**（只重算增益）。

### 5.3 关键设计决策

1. **只对 B 站 CDN 源接管**（白名单：`bilivideo.com/.cn`、`hdslb.com`、`cgvideo.com`、`acgvideo.com`）。
   YouTube / 本地文件 / alist 一律不接管、不改 `crossOrigin` → 零副作用。
2. **AudioContext 安全铁律**（脚本踩坑记录）：`ctx.state !== 'running'` 时**不接管**
   （否则音频被路由进挂起的 context = 彻底没声）。接管前先 `resume()`，失败就降级到「只衰减」的 volume 模式。
3. **降级链**：`GainNode 接管成功` → `audio.volume 只衰减`（`gain = min(0, gain)`，保留现有能力）
   → `保持原声`（测量失败 / 解码失败 / 段数 < 3 / DRM / 直播）。
   直播源沿用现有 `SkipR128Source`（`Source.biliLive`）。
4. **渐进式落位**（脚本 S2.2 的成果，直接抄）：先 4 段出初值（≈19 s 音频、覆盖 0–100% 时间轴），
   后台补齐到 12 段；精修值与初值差 ≥0.5 dB 才重新落位 → 首次可用时间从数秒降到亚秒级。
5. **不打断播放**：全部测量在播放中进行；未出结果时就是原声（`gain = 1.0`）。
6. **不污染用户音量**：增益只走 GainNode；同时把现有 `parseR128Gain` 里 `volume = 1` 的写法去掉。
7. **可选修掉符号 bug**（§2.2-5）：保留 `noBiliR128Gain` 快路径时，改为存 `measuredLufs = measured_i`、
   增益统一由 gain-planner 算，顺手把「越轻越小声」修正。
8. **ffmpeg 保留为回退**：非 B站源若想吃 r128，可继续走旧路径（默认关闭）；也可直接删掉以减小包体。

### 5.4 备选方案与取舍

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A（推荐）** | 抽样测量 + GainNode | 成本 ≈0.5 MB/首、可升可降、不碰播放控制、缓存可复用 | 需要动音频图（有明确风险控制） | ✅ 推荐 |
| B | 只把测量层换成抽样，仍写 `audio.volume` | 改动最小 | **只能衰减**，不满足「音量拉齐」；继续污染 defaultVolume；仍有 500 ms 跳变 | 仅作降级路径 |
| C | 油猴脚本适配播放器 DOM（hook `.music-player-audio`） | 不碰播放器源码 | 扩展页里的 `<audio>` 在扩展上下文中，油猴作用域/权限别扭；跨域 fetch 需 GM 权限；UI 割裂 | 不推荐 |
| D | 保留 ffmpeg 全片方案，只加缓存 | 零风险 | 单曲几十 MB 下载 + 全片解码，卡顿明显；不能提升 | 不推荐 |

## 7. 风险表

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | `crossOrigin='anonymous'` 后某源不带 ACAO → **静音** | 高 | 只对 B 站 CDN 白名单设置；实测 4 个 host 均 `ACAO: *`；异常即刻回退 |
| R2 | AudioContext 处于 `suspended` 时接管 → 全程没声 | 高 | 继承脚本铁律：`state !== 'running'` 绝不 `createMediaElementSource`；先 `resume()`（用户已点过播放，手势具备），失败则走 volume 降级 |
| R3 | `createMediaElementSource` 对同一元素只能调一次 | 中 | `WeakSet` 去重 + 失败标记；元素单例复用，天然只接管一次 |
| R4 | 长视频 sidx > 4 KB（实测 15.9 KB） | 中 | 两段式 Range：先 32 KB 读 box 头拿长度，不够再补一次 |
| R5 | 分片解码失败（多 moof 混拼只解出第一段） | 中 | 严格「init + 单段」独立解码（脚本实测结论）；失败段跳过，< 3 段则放弃归一 |
| R6 | FLAC / 杜比音源（30250/30251）可能解不了 | 低 | 沿用脚本 `excludeAudioIds`；无合适 AAC 档则跳过归一 |
| R7 | 首次测量期间音量未落位 | 低 | 渐进式：4 段初值 → 12 段精修；差值 < 0.5 dB 不动 |
| R8 | 主线程卡顿 | 低 | K 加权分块让出主线程（`lumChunkFrames=240000`）；60 s 抽样约几十 ms；解码在解码线程 |
| R9 | pglite 迁移：老用户 DB 无新表 | 中 | `migrateSQL()` 启动时跑 `migrations.json`；需实测「已存在旧库 → 新增表」升级路径，失败要能降级为不缓存 |
| R10 | 与「记忆播放位置 / 音量 / 播放模式」等既有特性冲突 | 中 | 不动 `currentTime`、不动播放控制、不写 `defaultVolume`；接管后跑一遍播放器回归清单 |

## 8. 测试方案（用两个音量差异大的视频）

1. **选片**：挑两条实测响度差 ≥4 LU 的 B 站视频。脚本文档已实测过的一对可作候选：
   - `BV1GJ411x7h7`（2009 老 MV，官方 `measured_i ≈ −13.5 LUFS`，偏响）
   - `BV1muab6rEbA`（110 分钟，脚本实测 `−18.69 LUFS`、真峰值 `+0.79 dBTP`，偏轻且过峰）
2. **基线**：关闭响度归一 → 两条连播 → 记录主观差异（或用录音算 RMS 作客观基线）。
3. **归一中**（目标 −14 LUFS）：同两条连播，**切换时整体响度一致**（±1 dB 内），中途无泵动。
4. **动态未压缩验证（关键，不能只看平均音量）**：
   - 同一首歌内挑「安静段 / 高潮段」，分别测 RMS，**归一前后差值应不变**（≤0.3 dB）；
   - 打印本次 `measuredLufs / truePeakDb / gainDb`，确认 `gainDb` 在整首播放期间是**一个常数**；
   - 与脚本自己的面板数值（同视频）对比，偏差应 ≤1 LU。
5. **回归**：音量滑块、进度拖动、切歌、播放模式、歌词、睡眠定时、`memoryEfficiency` 重载页面；
   `<audio>` 无静音、无爆音、无 `InvalidStateError`。
6. **性能**：首播到增益落位的时间（目标 <1 s）、抽样字节数（目标 ≈0.5 MB/首）、
   缓存命中落位时间（目标 ≈0）、播放期间无长任务（Performance 面板）。

## 9. 已知限制

- **纯线性增益，无压缩器/限幅器**：增益只在「真峰值 ≤ −1 dBTP」范围内提升，越界只衰减不提升，
  所以不会改变素材动态，但**也不会把已经过峰/爆音的素材修好**。
- **不支持直播**（无固定时长、无 DASH 索引）。番剧/影视在扩展里同样退化为普通 `dash` 资源，
  走同一套抽样路径；若只拿到 `durl`（试看片段等）→ 保持原声。
- **首播仍需等几百毫秒**（抽样 + 解码），期间播原声；看过的视频命中缓存瞬时落位。
- **抽样是统计估计**：极端不均匀的素材（例如只有结尾 5 秒很响）可能偏差 1–2 LU。
- **依赖音频 CDN 可达**：实测不需要 Referer，但风控变化会让测量失效 → 回退原声（不影响播放）。
- 与 B 站网页端「音量均衡」不会冲突（那是网页播放器自己接管 `<video>`，扩展里不存在）。
